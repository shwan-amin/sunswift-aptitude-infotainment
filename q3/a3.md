# Question 3

## 1. What makes a race car infotainment system different from a normal mobile app

The biggest functional difference between a car infotainment system and a normal mobile app is
that a mobile application wants the user's full engagement, while an infotainment system
displays vital information that must be read in a glance while driving. Latency needs to be as
minimal as possible since the display always has to show the current state of the vehicle,
while for mobile apps some features can be expected to make a user wait. It is updated
continuously by live telemetry rather than by client requests, and has to stay readable under
sun glare, vibration and heat and handle bad data itself, since the driver cannot restart it
mid race.

## 2. Four key principles of good infotainment design

Fail safe behaviour is the graceful handling of a subsystem dropping, where a clear error
message is displayed instead of the whole system freezing or crashing. This matters because
without it invalid data could still be displayed or acted on. An example is the GPS returning
null and the last valid position still being drawn as current, so the driver is trusting a location
the car has already previously visited.

Prioritisation of critical information means giving motor temperature, battery and speed the
largest and most permanent space on the screen, because the driver only has a glance to read
it. For example, having a overheating temperature warning be a small message in the corner of the display
will be hard to pick out for the driver, and they could miss it.

Predictability means the same data always appears in the same place, units and colours, with a
small set of states such as normal, warning and no data. Drivers read by position and colour
rather than labels, so if the dashboard is reordered when a value goes missing the driver could glance at
the usual spot for battery and read a different field instead.

Robustness to corrupted telemetry means treating every incoming packet as untrusted and
validating its type and range, since the network link is the least reliable part of the system.
Without it a value like "N/A" or a 300 km/h spike would be drawn straight onto the display and
stretch the chart until the real values are unreadable.

## 3. How I would test it

I would replay recorded telemetry at normal speed and then at ten or a hundred times that rate
to find where rendering falls behind the data. Error handling could be tested by
using faults on purpose by sending nulls, wrong types, corrupted strings and long gaps, 
checking the display still shows a valid state for each. Most of this is cheap to 
cover with unit tests since the testing/cleaning code is made of plain functions. 
Running for a few hours while watching memory and frame time would catch leaks
and rendering spikes a short demo would not. I would test the hardware on a vibration rig
and in direct sunlight at the angle it is mounted, which would test how
the system responds to hotter temperatures and environmental factors but this would be 
costly if a rig is not provided (and the weather would have to be hot, use a hotter
location if possible).
